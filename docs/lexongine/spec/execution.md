# Execution, timing and numerical behavior

First validate the logical DAG. Deterministic Kahn ordering picks the smallest declaration ordinal among ready logical nodes. Freeze this order before sharing. Canonicalize bottom-up, use a candidate hash plus full equality and eligibility, then map every logical occurrence to its physical producer. During each applicable update, walk the **logical schedule**: at a physical producer's first occurrence resolve it once; later occurrences reuse that outcome, but each logical occurrence is only reached at its scheduled position. Never independently topologically sort the shared graph for execution.

Counterexample: declarations S(0),p1(1),B(2),A(3),p2(4). Dependencies p1←S,p2←S,A←S,B←p2; p1=p2 eligible exact computation, A/B are separate effects. Logical order is S,p1,A,p2,B. Re-sorting the physical graph would run S,P,B,A. That reverses actions; if B fails, it wrongly suppresses earlier A. Correct projected execution is S,P,A,alias(P),B. If failure occurs between P's first occurrence and its alias, the alias remains Aborted/NotReached even though P has a partial publication. Do not broadcast all aliases when P first publishes.

Projection is topological: for any physical edge P→Q, the first logical representative of Q has a predecessor belonging to P; P's first occurrence is no later than that predecessor, which precedes Q. The unique-action subsequence and logical delivery boundaries therefore remain in the original order. This is a design argument; the independent graph probe is not a product proof.

At each reached logical occurrence, deliver its eligible request observations in declared request order, using that request's phase/mask. An observation handler is a unique effect boundary: its exception/failure stops the run; already delivered observations/actions remain partial evidence. Handler capabilities can inspect retained current/past immutable outputs, not advance other nodes or fetch future rows. If a caller needs observations buffered until a full step commits, that is a different explicit transactional interface, outside this slice.

Producer UpdateContext has no consumer phase. Consumers A evaluating from49 and B from60 can share the same [0,120) producer. At55 A is Evaluation and B is Warmup, while the producer receives one identical key55. A phase-dependent numerical operation must declare that schedule as semantic input, and is unsupported by the first ordinary typed numeric protocol. Unique action nodes own their explicit evaluation scope and the host gates them; this is not general conditional graph activation.

Sharing equivalence covers contract-deterministic logical values/statuses/timing/lineage, unique effects and computation-failure prefixes under compatible admitted resources. It does not promise identical physical allocation, cache-I/O, trace counts or operational failure positions between shared/unshared/cached executions. Every such operational failure still stops its run; all differences are reported. Removing work is precisely why physical counters can differ.

## Per-key outcomes and lifecycle

Per physical producer track last_resolved_key, state_advance_count, cached_delivery_count, last_published_key and current tagged outcome separately. An accepted warming update is resolved even when it has no successful publication. Keys are strictly increasing within the declared scope; same-key reads return the outcome without another call; a second scheduling attempt for a resolved key is a protocol failure.

| Required input state at current applicable key | Numeric callback | Outcome / next action |
| --- | --- | --- |
| All Published, compatible key/type/availability | Invoke once; private state may advance | Stage StepResult; validate; atomic complete-bundle swap |
| Required dependency Warming | Do not invoke | Resolve Waiting/Warming evidence at this key; no state advance |
| Inputs Published but own startup incomplete | Invoke once | Warming, state advance recorded; no payload |
| ValidAbsence | Only a declared supported outcome-aware policy could handle it; first numeric fixture supports none | Explicit required-value failure for arbitrary component ValidAbsence; declared source gaps are handled by the separate Strict/Skip timeline policy, not by this row |
| MissingRequired, Failure, future/mismatched/duplicate key or unsupported protocol | Do not invoke | Stop whole admitted run, preserve primary cause |

Failure/protocol violations take precedence over Warming when inputs disagree. Published means all declared outputs; absence/warming is bundle-wide. validate_pending performs all fallible checks/reservations before commit. commit performs only a preallocated nonthrowing ownership swap. Stage-port-1 then failure discards all newly staged ports; earlier valid producer publications are partial, not globally rolled back.

RunLifecycle={Created,Running,AwaitingCompletion,Finalizing,Terminal}; execution starts from Created; advance_one continues only while Running; AwaitingCompletion permits finalization but no further scheduling. Terminal cannot execute again. Fresh instantiate recreates state and required history. NumericalOutcome={Completed,Failed,Aborted}. IntegrationOutcome={NotFinished,Completed,Failed,Aborted}, set from the explicit standalone/host completion contract. AcceptanceStatus={Pending,Accepted,Rejected,Unconfirmed}. CachePublicationStatus={Disabled,NoNewEntries,Bypassed,Staged,Published,NotPublished,Unconfirmed}. Completed/Rejected is possible when required evidence fails; Failed never implies Accepted. Unconfirmed withholds acceptance/score and preserves the commit ID for reconciliation; it is not a proven rejected origin.

Preparation structural errors reject the submission. Source/operation incompatibility attributable to a request rejects that request and its dependents; independent admitted requests remain explicit. A globally over-budget combined plan rejects before instantiation rather than choosing a preferred subset. SourceKnownBoundViolation is compatibility, not corrupt canonical Price. Numerical outputs not available until computation retain explicit runtime validators.

## Explicit missing intervals

- Configuration uses required `missing_intervals="strict"|"skip"` on the source clock; components/requests explicitly declare acceptance of that policy. Lag additionally exposes `count_basis="complete_bar_updates"` (required supported value in v1). No automatic conversion/fill adapter is inserted. The existing no-gap XML fixture will explicitly use strict; a separate gap fixture uses skip.
- Provider metadata carries an expected interval contract, actual complete-record coverage and a bounded ordered gap ledger. SourceGap entries describe only declared absent expected intervals, never a malformed present record. Closed-market/nonapplicable intervals are determined by the source's explicit interval contract, not assumed to be missing by the engine.
- Full source validation still covers the requested scope. Under Skip, coverage acceptance checks that valid complete records plus declared gaps partition the expected scope exactly without overlap, unidentified holes, reordered/duplicate keys or incorrect instruments. Missing tails must be explicitly declared gaps or fail closure; gaps are never inferred silently from end-of-input. Corruption and numerical/type violations in present data remain fatal.
- At a source gap, resolve the host timeline event and log it once; no numerical callback, state update, lag shift, publication or action occurs. Retained state/windows stay intact. On the next complete bar, each applicable producer advances once on its original key. Arbitrary per-component ValidAbsence on an existing source update is not automatically a source gap.
- Count-history means N valid complete inputs including the current input; the preparation validator counts actual input records, not clock-key distance. Under Skip, N bars can span more than N intervals. Require sufficient usable history/readiness at the chosen first eligible evaluation bar; never silently move evaluation boundaries. Gaps within evaluation are explicitly skipped under compatible requests, not delivered as zero or stale observations. Reports record evaluated complete updates and skipped intervals separately.
- Within-run identity and persistent ArtifactIdentity recursively include source coverage/ordered gap ledger, missing policy, lag count basis and component/request compatibility versions. A strict artifact is not a skip artifact, even for identical observed values; omitted gap metadata invalidates compatibility.
- The numeric artifact outcome stream has one record per applicable complete-bar update; a separate bounded gap ledger covers the skipped keys. Manifest coverage validates their union against expected scope. Cache replay exposes the same SourceGap timeline events/no-computation boundary and same actual complete-input sequence. No checkpoint restoration or future-value access is introduced.
- Gap metadata/logging/cursor records and all expected timeline events are included in explicit resource/event/count limits before allocation; no unbounded run or tracing exemption follows from Skip. Endpoint/evidence/resource/ordinary computation failures retain existing whole-run fail-stop behavior.
- V2 notes: elapsed-time windows and lag, session calendars for real sources, explicit filling/reconstruction, gap-size/staleness limits and reset/recovery algorithms. The first standalone synthetic fixture does not claim those integrations are implemented.
